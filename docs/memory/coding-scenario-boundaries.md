# Scenario boundaries and defensive logic

先明确产品支持的使用场景、运行假设与责任边界，再围绕这些前提实现功能。不要顺便为未经需求或事实支持的假想异常增加防御逻辑，也不要把越界操作自动纳入产品保证。

例如，用户自行编辑本地 CLI 的 JS 产物、手工破坏运行文件或绕过约定入口，不意味着产品必须增加探测、修复、兼容或兜底分支来保证这些操作后的行为。无法也无需穷尽防范用户对本地程序的任意改写。

这不等于禁止必要的错误处理。约定场景内实际会发生、直接影响功能正确性或资源占用的失败仍需处理；已明确要求的鉴权、凭据保护等边界继续遵守。判断依据是具体场景和需求，而不是“万一可能发生”。

**Why:** 到处堆叠防御分支会扩大产品范围、增加代码复杂度，并给维护和迭代带来持续成本。
**How to apply:** 添加检查、恢复、重试或兼容分支前，先说明它对应哪个受支持场景、有什么需求或事实依据，以及为什么必要。没有依据的分支不添加；明确写出不支持的场景，不用额外防御代替范围界定。遇到已发生的问题先定位根因，避免用兜底掩盖根因。
