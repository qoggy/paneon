# Reusable panel examples

Provide ready-to-run standard panels and useful scene examples as resources of the product skill, following [the skill asset boundary](agent-skill-assets.md). Standard choice and information-collection pages accept task-specific data without requiring the agent to rewrite TSX. The choice page must support option-only answers, optional explanations, independently written answers, and multiple sequential questions in one page. Submit all answers together at the end; navigating between questions retains editable page-local drafts without emitting answer events. A successful final submission saves one event containing the complete set of final answers. One instance represents one questionnaire round; start a new round with a new instance and link, preserving the previous round's question/answer association. File input is a creation-time JSON snapshot: editing the original parameter file does not change an existing instance, and reload/restoration uses its saved params. The approved --params-file capability remains unimplemented until the active change is applied.

The information-collection panel presents all fields on one page and submits the complete form together, without a step-by-step grouping flow or partial field-answer events. Field types and detailed validation remain under contract alignment.

The local Git review page is a standard panel and must distinguish multiple repositories. It covers current staged/unstaged/untracked changes, branch-introduced changes, and direct committed-version comparisons. Its initial navigation is confirmed below; detailed history, refresh, and annotation contracts remain under alignment. The interactive data table is also a standard skill panel: callers supply task-specific data without rewriting TSX. Cell data is read-only, while selection supports rows, columns, and cells; feedback distinguishes those kinds using the instance's original zero-based rows indices and column keys. Callers do not supply rowKey or a required id field; presentation sorting, filtering, and pagination preserve original indices, including for duplicate records. The table reuses the shared selection/annotation capability and allows mixed targets and multiple independent annotations; detailed validation and location contracts remain under implementation design. The user accepted a real GitHub PR scene example and exploratory content-review/concurrency pages. Detailed page contracts remain under alignment in the active change. Existing repository examples are the pre-migration implementation; this convention does not claim those new resources have been delivered.

The Git page also provides current-branch commit history, per-commit changed files and diffs, precise editable annotations on changes/text, and an agent-specified initialView. Its confirmed view types are changes, history (optionally a commit), and compare (branch or commits mode); file can locate a repository-relative file, and omitted initialView opens the first repository's working changes. Initial navigation does not lock the person into that view. Follow Git ignore semantics for untracked files without hiding already-tracked changes. Allow repeated draft edits and send the annotation set only after explicit submission; correcting submitted annotations requires another explicit submission and appends an identifiable revision without rewriting earlier events. Precise anchor and revision-result fields remain under contract alignment.

Include at least one real CLI/OpenAPI integration example. The user selected gh CLI for the initial iteration. Build a repository/PR panel showing lists, details, and actions. The PR example reads GitHub content only; explicit review requests and opinions go to the current agent through Paneon events. Do not publish GitHub comments/reviews or add approve, merge, close, or other GitHub write actions to this example. Verify the actual commands used when implementing the example. Document prerequisites and usage, and demonstrate both direct server actions and explicit agent events.

Explanatory examples may be one-off pages with their topic, fixed data, and initial values directly in TSX. The concurrency-and-queue example follows this approach: agents copy or modify source, while people explore page-local controls. Do not turn it into a parameterized standard panel or add dedicated business input/configuration files. This does not remove necessary inputs from other examples such as the GitHub PR repository.

The one-off LeapArray explanation example references [alibaba/Sentinel](https://github.com/alibaba/Sentinel). Design documents and example pages must not expose a developer-machine Sentinel checkout path; investigate the source when implementing the page, without requiring advance product decisions about its algorithm details.

**Why:** Examples make the component library easier to use and demonstrate that panels can connect to existing tools with ordinary code.
**How to apply:** Keep tool calls, data conversion, and business behavior in panel/example modules. Do not add a CLI executor, business monitoring, or log management to the core. Keep isolated demonstration backends for automated checks without external accounts; do not use component checklists, counters, or mock releases as the primary user-facing scene examples.
