## Implemented ownership and contracts

- `git.ts` has no module-level session/snapshot/listing/history business Maps. Git queries accept explicit configuration and requests/descriptors; ephemeral Maps used while parsing refs are ordinary per-call computation.
- `readGit(params, request, signal?)` resolves the first branch tip. `historyContext:{repositoryId,branch,tip?}` plus `offset/pageOnly` is sufficient for fresh backend paging. Initial refs/decorations remain in browser memory; later pages are decorated from that frozen catalog. A large catalog is not resent per read.
- `readGitFile(params, fileDescriptor, signal?)` accepts the listed repository/view, paths, entry modes/blob OIDs, working/conflict flags and file identity. Returned `listingId` is browser display scope only; it is not a backend read input. Working bytes are captured when the file is opened. Fixed history/compare reads use explicit objects; default first-parent/root/merge-base semantics and path/symlink/binary/conflict boundaries remain. Explicit history parents must be actual parents.
- Independent `GitBranches`, `GitCommitGraph` and `GitChangedFiles` accept semantic repository/version/selection props and own their named-action reads. Their corresponding hooks support custom layouts. The built-in page uses the module's `useGitReader` boundary while retaining its original JSX and selection/loading orchestration. `assets/examples/git-components/panel.tsx` demonstrates independent use.
- `DiffView` with two strings and no `sourceId` uses no FeedbackProvider. Supplying `sourceId` opts into existing annotations; PR callers retain their old integration without a protocol change.
- Browser `buildGitFeedback` retains the original displayed model and constructs normalized targets plus deduplicated source/evidence. Pure `validateGitFeedback` uses the current event and explicit repository configuration only. It validates source association, exact line counts, UTF-16 quotes/graphemes, hunk reconstruction and conflicting/duplicate evidence, without Git/filesystem or old-state lookup. File targets need metadata/hashes only; line/text targets carry complete selected original lines; hunk targets carry patch and both composing fragments.
- Hashes label whole-content versions. Selected fragments establish internal consistency and do not prove whole hashes or Git provenance. `comment`, complete `replacesEventId`, explicit success receipts, failure-retained drafts and the existing 65536 UTF-16 event / 262144 UTF-8 request limits remain. No persistence, automatic retry, truncation or implicit splitting was introduced.

Exact props/request/result/event examples are in `skills/paneon/references/git-review.md` and this change's `design.md`.

It proves that a subsequent file can be read and a later page can be fetched from fixed tip without a preloaded Map, and an annotation built from old browser text is accepted after the working file changes. ## Failures investigated during development

- A fresh-process test initially selected an allow-empty tip, so its file list correctly had no files. The fixture now explicitly selects its known changed commit while retaining the generated graph tip. No product fallback was added.
- The first independent component browser test waited for a root row already present in the old graph. It now waits for the old feature row to disappear after branch selection. No timeout increase or retry was added.
- A real Git browser run exposed `undefined` optional fields in a subsequent pinned-history result. Runtime JSON results disallow undefined. The reader now omits absent fields, including unborn-tip context and detached current branch, and the subprocess test explicitly runs the runtime's `jsonValue` boundary. Full browser regression then passed.
- GPU screenshot comparison initially produced 21/24 byte-identical pairs. The remaining pairs differed at 2, 12 and 1 pixels, localized to rounded button/icon antialiasing; exact DOM and rectangles were identical throughout. Original evidence remains in `/tmp/paneon-stateless-visual` and `/tmp/paneon-stateless-visual.log`. Fixing Chrome to software rasterization (not adding a pixel threshold or retry) produced 24/24 strict byte matches; that deterministic mode is now the test's explicit configuration.
- PR complete workflow had a stale English `Head <sha>` locator while its fixture sets zh-CN and the existing product shows `当前版本 <sha>`. A baseline a32404d skill fixture independently confirmed zero English matches and the visible Chinese label (`/tmp/paneon-stateless-pr-baseline-locator.log`). Only that test locator changed; PR source/locale/protocol did not. All three cases then passed.
- New screenshot test formatting initially failed ESLint/Prettier. The test was formatted; final lint has no errors and final format check passes.
