# Panel resource lifecycle

## 已确认的决定

2026-10-25，用户接受“延迟恢复 + 有界的每面板子进程驻留”并授权实施，明确废弃 B14 的全局两个执行位置方案。B14 原文使用 worker_threads，并非已实施的两个进程；两者均不作为本次方案。

- **B13 保留**：固定面板总数、同时活跃不超过十个时，历史面板无需手动 close，后台执行、监听与清单缓存有界，并兼顾切回与 reload 体验。
- **B14 废弃**：不迁移到全局两个线程，不新增 ctx.cwd、单调用默认 30 秒时限、每任务 signal、100 次调用/五分钟寿命轮换。
- **本次批准**：启动懒恢复、独立静态产物/清单读取、索引查询、编译串行、有硬上限的 LRU 驻留、容量满时有界等待及相关竞态验证。
- **B15 仍待决定**：本次不更改页面隐藏、通知重连、可选 refreshMs 或协议保活行为。
- **C2 后续单独批准**：本驻留改动未包含磁盘删除；2026-10-25 用户随后批准 [reclaim-generated-artifacts](../reclaim-generated-artifacts/design.md)，按当前 revision 保留、失败/close 清理和 listen 后清扫实施。源码、SQLite 事件和用户数据仍不删除，不迁移数据库或重置运行目录。

原 B4/B6/B7/B8/B10 继续适用：尚未首发；批注依原文与版本；页面持有展示数据；草稿在浏览器；业务代码不得结束 HTTP 主服务。旧 B12 按次销毁同样保持撤回。

## 执行与监听的上限

默认最多十个驻留面板位置，每个位置对应一个面板及当前 revision，可以只有源码 watcher，也可以同时有一个执行子进程。业务代码只在子进程执行，保留 fork 的独立 cwd、现有模块加载方式、环境级 signal、驻留期间同面板异步调用重叠。不会因为并发三个 action 而改成两个执行、一个排队。

位置从开始初始化就预留；退出中的位置在 watcher 关闭、执行进程 exit 后才释放。需要新面板而容量已满时，只淘汰没有初始化、编译、action 或事件校验在途的最久未用位置。WebSocket 存在不固定位置，协议 ping/pong 和历史事件读取不刷新执行驻留时间。

所有位置忙时，新增面板的接纳按 FIFO 等待，最多 32 项、等待 10 秒。满队列或等待超时返回 RUNTIME_BUSY，已超时项不在之后执行。已有面板仍可加入当前进程的并发调用。这里限制驻留面板，不承诺限制作者的单面板请求并发或任意子孙进程。普通 LRU 不中止在途 mutation；显式 reload、close 和 server stop 沿用原来的停止边界，不增设旧调用完成/接管保证。

编译另有一个位置及同样有界的等待队列；类型检查、前后端构建与作者元数据检查在 CompilerProcess/隔离元数据子进程内执行。常驻执行进程最多十个，编译期间可另有一个 compiler 和一个短时元数据 worker。此数量不是总 RSS 的字节预算，也不是任意业务子进程上限。

不添加按空闲秒数清零、按调用次数回收或强制 action 执行期限；没有容量压力时允许有限保温。默认数值是初始容量策略，不是已经证明适合所有机器的最佳参数。

## 懒恢复与访问路径

<!-- prettier-ignore -->
| 操作 | 行为 |
| --- | --- |
| 服务启动/restore | 不遍历求值或编译历史源码，不起历史 worker/watcher；数据库的 running 表示逻辑打开，不代表进程驻留 |
| list / inspect | 数据库目标查询/分页投影；按需读取磁盘 manifest，不起执行 worker |
| 静态页面/JS/CSS | 由实例当前 revision、磁盘清单和资源白名单提供，不依赖 live worker |
| 状态 WebSocket | 保留现有通知；watch 面板按容量恢复监听并检查停驻期间源码，不固定驻留位置，不仅为通知启动执行 worker |
| action / 提交事件 | 按需恢复执行；保持原始 Zod schema 校验，不以 JSON Schema 替代业务 refine |
| 读取历史事件 / ack | 只依赖数据库与原有投递游标；源码缺失也不应因此无法读取历史 |
| 显式 run / reload | 仍编译并校验；reload 替换执行环境、不自动重放 mutation |
| close / stop | 先禁止新工作，撤销等待、停止初始化/编译与执行，等待真实退出，保留已提交事件 |

源码更新仍由 Vite watcher 触发编译和原有页面状态通知。只有监听而没有执行环境的面板，源码更新后仍不额外创建常驻执行 worker。监听被 LRU 淘汰后，下一次 watch 激活或执行检查自己的依赖摘要，变化才编译；no-watch 保持只显式 reload 源码的语义。Paneon 版本变化或产物缺失在真正使用时处理，不在 restore 批量重建。

热面板的源码订阅共享一个惰性 Vite watcher，各面板独立释放自己的订阅；共享监听实现见 [reduce-bundles-and-fix-source-watching](../reduce-bundles-and-fix-source-watching/design.md)。自动更新与 watch 重新激活的构建复用条件见 [skip-unchanged-watch-builds](../skip-unchanged-watch-builds/design.md)。历史面板数量不应决定后台常驻资源量；容量约束优先于保留空闲模块状态。

## 产物

沿用 ~/.paneon/panels/<instanceId>/sha256-<revision>/manifest.json 及 client/server 目录。清单缓存最多 32 份、序列化内容合计 8MiB，超大清单读取后不驻留；不把该数值说成精确 JS 堆预算。面板记录按主键读取，只解码目标 params；列表使用已有 SQL 分页投影。

冷唤醒复用有效的 server.js，不走强制 reload；唤醒后重新检查调用携带的 revision 与关闭状态；不能把旧 revision 请求悄悄交给新 handler。事件校验返回后，写 SQLite 前再检查身份，避免 reload/close 期间提交到错误版本。

模块 Map/对象内容和返回后后台工作原本是“可运行但不保证”；LRU 新增了由其他面板活动触发的回收边界。回收会丢模块状态、可能终止或失去对后台工作的管理，不承诺任意子孙进程自动退出。浏览器展示数据/草稿不因执行环境回收而卸载。

## 内置 PR 示例

PR 示例原先依赖进程内 session/snapshot Map；LRU 会让仍在浏览器中的旧批注失去提交依据。本次仅适配内部数据契约：每个 action 创建请求内读者，由浏览器传入所需的固定版本详情、比较和被引用原文，重建当次校验上下文。旧原文不因 GitHub 最新内容变化而改写，不引入远端真实性认证；只保留既有来源/位置校验并检查输入内部一致性。相关 ID 在生成与 schema 解析时使用一致字段顺序。PR 界面、布局、批注和审阅请求操作不变。

只发送反馈实际引用的来源以及重建 diff 所需原文，不发送冗余渲染模型。原有 256KiB 完整请求和事件限制继续生效；过大输入明确失败并保留草稿。请求内派生缓存不会作为跨调用必需业务状态。

## 验证范围

- 历史记录和源码缺失时启动零历史执行/监听；inspect、静态产物和事件不因执行冷态而失败。
- LRU 顺序、忙位置保护、FIFO、有界等待、过期工作不补执行、starting/retiring 计数、同面板并发、编译峰值一个。
- 淘汰再唤醒复用产物；显式 reload 重置状态；watch 停驻期间源码更新、no-watch、旧 revision 拒绝。
- close/stop 撤销排队和初始化，真实进程退出；事件 schema 和提交身份检查保留。
- 多轮使用与 1/5/10 活跃面板验证资源数量饱和；真实 Chrome 覆盖冷态页面与普通动作输入和原有批注交互。RSS/FD 只能据实报告样本，不把数量限制当成绝对内存保证。
